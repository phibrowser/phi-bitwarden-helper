# PhiBitwardenHelper

Out-of-process Bitwarden vault helper for [Phi Browser](https://github.com/phibrowser),
written in native Rust so it can link the Bitwarden SDK directly.

## Why this exists

Phi needs a real Bitwarden vault engine (login / unlock / lookup / TOTP) to back
its credential provider and agent credential surface. The obvious path — linking
Bitwarden's `sdk-swift` into the macOS app — is a dead end: the published
`BitwardenFFI.xcframework` ships **iOS slices only** (`ios-arm64`,
`ios-arm64_x86_64-simulator`), no macOS slice, so it cannot link into a macOS
target.

Instead, this is a standalone **Rust** binary that links the SDK's own Rust
crates natively — no UniFFI, no xcframework, no macOS-slice problem. Phi spawns
it at `<App>.app/Contents/Helpers/PhiBitwardenHelper` with one end of a
`socketpair(2)` as fd 0 and talks framed JSON over it — no filesystem socket
exists, so no other process can connect to or impersonate either side. Phi links
none of this and stays Apache-2.0; this helper is GPL-3.0 (it links the GPL
SDK), and the two communicate only across a process boundary.

## SDK pin

| | |
|---|---|
| SDK source | `github.com/bitwarden/sdk-internal` |
| Tag | `rust-v3.0.0` (commit `7fd530e`) |
| Matching Swift release | `sdk-swift` `v3.0.0-7165-e504886` |
| Crates linked | `bitwarden-core`, `bitwarden-vault` |
| Phi patches | `sdk-patches/` (applied on top of the tag, in order) |

The SDK checkout this crate builds against lives at `../sdk-internal`: the
upstream tag with the `sdk-patches/` series applied (`git am sdk-patches/*.patch`).
The patch files in this repo are the canonical record of Phi's SDK changes —
regenerate them with `git format-patch` whenever the patched branch changes, so
the helper repo alone (plus public upstream) is the complete Corresponding
Source for a shipped binary.

`Cargo.lock` is **inherited verbatim from sdk-internal @ rust-v3.0.0**. This is
required: consuming the SDK's crates as git dependencies does not inherit their
lockfile, and cargo otherwise resolves newer, API-incompatible RCs of the
RustCrypto pre-release crates (`ml-dsa`, `der`, `spki`, `pkcs8`, …) and the build
fails. Do not regenerate the lock from scratch; update it in lockstep with the
SDK tag.

## Building

```sh
# Default build — stub engine, no SDK. Fast; validates the protocol.
cargo build --release

# SDK-backed build — links the pinned Bitwarden SDK (GPL).
cargo build --release --features bitwarden-sdk
```

Output: `target/release/PhiBitwardenHelper` (a plain Mach-O executable).

### Universal binary (for Intel + Apple Silicon)

```sh
rustup target add aarch64-apple-darwin x86_64-apple-darwin
cargo build --release --features bitwarden-sdk --target aarch64-apple-darwin
cargo build --release --features bitwarden-sdk --target x86_64-apple-darwin
lipo -create \
  target/aarch64-apple-darwin/release/PhiBitwardenHelper \
  target/x86_64-apple-darwin/release/PhiBitwardenHelper \
  -output PhiBitwardenHelper
```

## Integrating with Phi

Drop the built `PhiBitwardenHelper` into the app bundle at
`Contents/Helpers/PhiBitwardenHelper`. Phi's Swift `BitwardenHelperClient`
already spawns exactly that path with a socketpair on stdin and speaks this
protocol, so **no Swift changes are needed** — it does not care which language
produced the binary. (In the Phi Xcode project, replace the Swift
`PhiBitwardenHelper` target's product in the "Copy Bitwarden Helper" build phase
with this prebuilt binary, or copy it in via a script phase.)

`install-into-phi.sh` does this end to end: it rebuilds the helper, refreshes
`phibrowser-mac/Vendor/` (the binary **and** the GPL material below), and
hot-swaps the newest built app. Phi's copy phase bundles all three vendored
files.

## Distributing binaries (GPLv3 §6)

Every shipped Phi build that bundles this helper must carry, in
`Contents/Resources/` (codesign rejects non-code files next to the binary in
`Contents/Helpers/`):

- `PhiBitwardenHelper-LICENSE.txt` — the complete GPLv3 text (this repo's
  `LICENSE`).
- `PhiBitwardenHelper-SOURCE-OFFER.txt` — the Corresponding Source designation,
  generated by `install-into-phi.sh` from `dist/SOURCE-OFFER.txt` and stamped
  with the exact commit the binary was built from.

Release checklist — each item blocks distribution:

1. **Publish this repository** at the URL named in `dist/SOURCE-OFFER.txt`
   before shipping; the offer designates it as the source location, and it must
   be self-contained (source, `Cargo.lock`, `sdk-patches/`).
2. **Re-vendor from a clean checkout** so the shipped offer carries a real
   commit hash — a `-dirty` stamp in `PhiBitwardenHelper-SOURCE-OFFER.txt`
   means the shipped binary is not reproducible from published source.
3. **Export every SDK patch.** `sdk-patches/` must reconstruct the exact tree
   the binary links: a Phi commit that lands on `phi/rust-v3.0.0-patched`
   without being exported ships a binary nobody can rebuild from the published
   source. `install-into-phi.sh` refuses to vendor when the two disagree;
   verify by hand with

   ```sh
   git -C ../sdk-internal format-patch 7fd530e4..phi/rust-v3.0.0-patched -o /tmp/p
   diff -r /tmp/p sdk-patches
   ```
4. **Legal sign-off** on (a) the separate-process boundary: the FSF FAQ treats
   sockets/pipes between separate programs as the customary separation, but not
   as solely determinative — the semantics of the communication matter; and
   (b) the offer text itself. The "aggregation" position in the design docs is
   a design intent, not a legal conclusion.

## Protocol

One inherited `socketpair(2)` connection on fd 0, held for the helper's
lifetime (EOF means Phi went away and the helper exits). Wire frames are a
4-byte big-endian length prefix followed by a JSON object.

1. On startup the server sends `{"challenge": "<hex>"}`.
2. The client replies `{"challenge_response": "<same>", "client_version": "…",
   "protocol_version": 1}`.
3. The client sends requests `{"protocol_version": 1, "request_id": "…",
   "method": "…", "params": {…}}`.
4. The server replies `{"ok": true, "result": {…}, "request_id": "…"}` or
   `{"ok": false, "error": {"message": "…"}, "request_id": "…"}`. Each request
   runs on its own thread, so replies may arrive out of order; the echoed
   `request_id` is what matches them up.

Methods: `status`, `login`, `unlock`, `lock`, `logout`, `lookup`, `getTotp`.

## Status

- **Protocol + stub engine** — complete and tested end-to-end against Phi's client.
- **SDK linkage** — the pinned SDK compiles for macOS and links (verified on
  arm64). The SDK-backed engine (`src/bitwarden_engine.rs`) currently stubs the
  vault operations; wire them against the SDK's async client API with the
  compiler (`client.auth()` login, `client.crypto()` unlock, `client.vault()`
  sync + decrypt).
